# quasarr/storage/setup/ - Setup Flows

## Purpose

First-run and reconfiguration flows: each prerequisite gets a temporary web server that blocks startup until configured or, where allowed, explicitly skipped, plus reusable save/verify handlers consumed by the main config API.

## Ownership

`path.py`, `hostnames.py`, `jdownloader.py`, `flaresolverr.py`, `arr.py`, `radarr.py`, `sonarr.py`, `notifications.py`, `timeouts.py`, `filecrypt.py`, `crypter_blocks.py`, `common.py`; `__init__.py` re-exports everything for `quasarr/__init__.py` and `quasarr/api`. `carbon.py` is the sibling Carbon render module for the eight temporary-server `GET /` forms - it owns no routes itself, matching the `api/*/carbon.py` shape.

## Local Contracts

- Module shape: pure `save_*`/`get_*_data`/`refresh_*`/`is_*_skipped` handlers reusable by the main API; the setup-blocking modules (path, hostnames, flaresolverr, radarr, sonarr, jdownloader) additionally provide a `*_config(...)` function that builds a temporary Bottle app (`add_no_cache_headers` + `setup_auth` applied) and returns `Server(...).serve_temporarily()` - signatures vary (`radarr_config`/`sonarr_config` also take `required_sites`; `hostname_credentials_config` takes `shorthand` and `domain`). `notifications.py`, `timeouts.py`, `filecrypt.py`, and `crypter_blocks.py` provide only save/refresh handlers, no temporary server. Completion is signaled by setting `quasarr.providers.web_server.temp_server_success = True` inside a route handler.
- Startup order in `run()`: path → hostnames (must end with ≥ 1 valid hostname) → per-source credentials (skippable, table `skip_login`) → FlareSolverr (skippable) → required *arr client → JDownloader (NOT skippable) → notification + timeout + filecrypt + linkcrypter-block init → API key generation.
- `hostnames.py::build_hostname_rows(shared_state)` is the pure per-source data builder: source order, status/details/timestamp, login/credential *support* (a bool plus which `credential_section` holds it - never the user/password values themselves), FlareSolverr requirement, language, categories, invite/account flags, and skip state, sourced from `quasarr.search.sources.helpers.get_source_metadata()`. `hostname_form_html()` (Classic renderer), `get_hostnames_data()` (the API's secret-free `GET /api/hostnames` projection), and `api.config.carbon.build_hostnames_model()` (the Carbon Hostnames view) are all thin consumers of it; HTML/JS escaping and the Windows flag-emoji-to-SVG fallback (`providers.html_images`) live only in `hostname_form_html()`, never in the builder.
- Active skip flags live in tables `skip_login` and `skip_flaresolverr`; they are stored only as the string `'true'` and cleared by deleting the row. Never write `'false'` - readers treat any stored value as skipped via truthiness. Radarr/Sonarr read legacy skip preferences for boot migration, but setup offers no skip route. (The `'true'`/`'false'` pair convention applies to notification-settings, timeout-slow-mode, and filecrypt-enabled tables instead.)
- `arr.py` asks the user to choose Radarr or Sonarr only for hostnames that support both movie and TV searches; a movie-only or TV-only hostname still requires its matching client. Legacy skip preferences are honored: a skipped client with matching configured sources emits a boot warning; both skipped emits an error and reopens required setup.
- `arr.py` also owns the shared *arr requirement check so the dashboard, hostname editor, and session usability treat either configured client as sufficient for a dual-category hostname.
- Radarr/Sonarr startup forms require both fields server-side as well as in HTML. Main settings reject clearing a client required by an exclusive hostname or when the other client cannot cover every dual-category hostname; either client can be cleared for dual-only hostnames when the other remains configured. Runtime search guards remain the final protection against missing clients. `is_*_skipped()` reads legacy skip preferences for boot migration.
- `timeouts.py` refresh calls `constants.apply_timeout_slow_mode_settings()` - the only sanctioned way timeouts change at runtime.
- `filecrypt.py` is the filecrypt kill switch: table `filecrypt_enabled` (constant `FILECRYPT_ENABLED_TABLE`), default `True` when unset, refreshed into `shared_state.values["filecrypt_enabled"]`. `quasarr/downloads/__init__.py` reads that cached value to drop filecrypt links at grab time - this module does not touch download logic itself.
- `crypter_blocks.py` owns table `crypter_block_settings` (constant `CRYPTER_BLOCK_SETTINGS_TABLE`). It refreshes `mode` into `shared_state.values["crypter_block_mode"]` (`defer` by default, `fail` for legacy behavior) and decimal `cooldown_hours` into `shared_state.values["crypter_cooldown_hours"]` (default/minimum 24). The two legal mode strings come from `providers.crypter_cooldowns`, which also owns the runtime gate that consumes them. Invalid or omitted POST fields preserve their current values; a malformed non-object JSON payload writes and refreshes nothing.
- Radarr/Sonarr verification resolves fixed IMDb IDs through the respective API client and caches the client in shared_state via `set_client` before `is_*_configured` checks run.

## Work Guidance

- Setup pages render through `providers.html_templates` (`render_form`/`render_success`/`render_fail`); restart UX uses `common.render_reconnect_success`. `render_success`/`render_fail` and `render_reconnect_success` each dispatch Classic/Carbon via `page_dispatch.render_page` - the Classic branch is byte-identical to the body before Carbon dispatch was added, so every setup flow above keeps its exact Classic output while gaining Carbon rendering automatically whenever the UI preference/env/query/cookie resolve to `carbon` (that resolution already works during setup: `load_ui_preference()` runs in `quasarr/__init__.py::run()` before any setup flow, and `setup_auth()` registers the same public static routes Carbon assets need). `render_reconnect_success`'s Carbon branch reproduces the exact countdown-then-`HEAD /`-poll timing (1000ms ticks, `cache: 'no-store'`, 500ms pre-reload pause) as an external `carbon.js` action (`data-action="reconnect-poll"`) instead of the Classic inline `<script>`, which strict Carbon CSP forbids. The same dispatch pattern extends to each temporary app's own `GET /` form (previously Classic-only via `render_form`).
- The dashboard in `quasarr/api` replicates hostname-status logic from here - keep them in sync.

## Verification

- Full unit suite: `uv run python -X utf8 -m unittest discover -s tests`; setup flows themselves are exercised manually via `uv run Quasarr.py` first-run

## Static assets / setup integration

- `setup_auth(app)` in `quasarr.storage.setup.common` must call `setup_static_routes(app, immutable=False)` so every temporary setup server exposes the same `/static/<filename:path>` endpoint.
- The static route remains public (`@public_endpoint`) under active auth; setup auth still protects non-public routes.

## Carbon dispatch for all eight `GET /` setup forms

- Every `*_config()`'s `GET /` route now follows the `api/*/__init__.py` pattern exactly: the pre-existing Classic body is renamed to a sibling `_classic_<name>_form()` function at its original nesting depth (never re-indented, to guarantee the Classic HTML stays byte-identical down to whitespace inside multi-line string literals), and a new thin route callback calls `render_page(page_id, carbon, _classic_<name>_form, shared_state=shared_state)` with a callback-local `from quasarr.storage.setup.carbon import render_setup_<name>` import. `page_id`s: `setup-path`, `setup-hostnames`, `setup-hostname-credentials`, `setup-flaresolverr`, `setup-arr-client`, `setup-radarr`, `setup-sonarr`, `setup-jdownloader`.
- `carbon.py`'s `render_setup_*()` functions all return `carbon_templates.render_carbon_simple_page(...)` (no side nav/header/CAPTCHA badge, matching every other auth/system page) - never `render_carbon_html`. That shell has no `#cds-modal`/`#cds-toast-region` landmarks by design (`test_carbon_templates.py` pins their absence), so these pages do not use `window.showModal`/`showToast`; every interaction is either a real `<form method="post" action="...">` (byte-identical POST contract to Classic, full-page navigation into the existing `render_success`/`render_fail`/`render_reconnect_success` response) or a small setup-only `carbon.js` action for a genuinely dynamic step.
- The Hostnames setup page reuses `storage.setup.hostnames.build_hostname_rows()` (never re-derives row status) and mirrors `api/config/carbon.py`'s row markup/CSS classes, but is intentionally simpler than the main Hostnames page: no modal-based status dialog - each row has an inline collapsible `.cds-hostname-credentials` Details panel instead. The uncontrolled per-row `details` exception text (may embed a configured hostname) is never rendered into the initial page HTML; it is fetched fresh, only on Details expand, from `GET /api/hostnames` (a **new** route added to the setup app itself, mirroring the main app's identical route in `api/config/__init__.py` - the setup app previously exposed only `POST /api/hostnames` for saving) and lands solely as `textContent`. Stored credentials never reach the page: the credential fields under a Details panel always render blank.
- New `carbon.js` IIFE `bootstrapCarbonSetupFlows` owns six setup-only actions, deliberately named with a `setup-` prefix distinct from `bootstrapCarbonHostnamesAndCategories`'s same-shaped main-page actions (both listen globally; reusing a name would double-fire): `setup-hostnames-import`, `setup-hostname-toggle-details`, `setup-hostname-credentials-check`, `setup-credentials-skip`, `setup-flaresolverr-skip`, `setup-jd-verify`. It is inserted **before** `bootstrapCarbonTime`/`bootstrapCarbonDownloads`, not appended at end of file, to preserve the "last two IIFEs, nothing after them" invariant `tests/test_carbon_downloads.py`'s marker-to-EOF slicing depends on (see that file's notes on the marker-to-EOF slicing contract). Path, Radarr, Sonarr, the *arr client selector, and JDownloader's final Save step need no custom JS at all - plain native Carbon-styled `<form>`s reproduce Classic's existing full-page POST/redirect flow.
- Temporary setup apps do not register `/ui/carbon` or `/ui/classic` (those cookie-setting routes exist only on the main app in `quasarr/api/__init__.py`) - the Classic footer's fixed "Carbon UI" link and the Carbon simple-page footer's "Switch to Classic UI" link both 404 if clicked on a setup temp server. `?ui=carbon`/`?ui=classic` query params and `QUASARR_UI` env var are what actually work during setup, and every native-form POST necessarily drops that query param. The *mechanism* (env beats query beats cookie beats cached preference beats default, per `ui_preference.get_active_ui()`) predates the Carbon dispatch added to these setup forms, but the *visible symptom* is new: before that, the `GET /` form itself was always Classic (there was nothing to select), so a `?ui=carbon` first-run user saw a consistently Classic flow throughout. Now that same user sees the form render in Carbon and then the very next page (the `render_success`/`render_fail`/`render_reconnect_success` result of their POST) flip back to Classic, because that POST carries no query string - a real, visible mid-flow inconsistency, not merely a pre-existing one made more noticeable. It only resolves for the rest of the flow if `QUASARR_UI` is set as an environment variable.
