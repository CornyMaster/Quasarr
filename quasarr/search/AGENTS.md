# quasarr/search/ - Search Side

## Purpose

The Newznab-facing search layer: `get_search_results()` fans a single *arr request (IMDb-ID search, phrase search, or feed pull) out in parallel across all discovered source modules, caches per-source results, merges/sorts/filters/paginates them, and returns releases whose `link` points back at Quasarr's own `/download/` endpoint with a base64 payload.

## Ownership

- `__init__.py` - orchestrator: the three search branches, `SearchExecutor` (thread-pool fan-out + per-source status badges), and the module-private `SourceTaskOutcome`/`_Completion` envelopes its futures carry
- `cache.py` - `SearchCache` (bounded TTL/LRU result cache) and the `search_cache` singleton, both re-exported from `quasarr.search`
- `runtime.py` - process-local search instrumentation: `SearchRuntime`, the `search_runtime` singleton, `read_process_memory()`
- `reclaim.py` - optional `IdleMemoryReclaimer` quiet-period scheduler and the cached Linux/glibc `malloc_trim` probe, both re-exported from `quasarr.search`
- `singleflight.py` - `SearchSingleFlight`, `SharedWork`, and the process-local `search_singleflight` registry, re-exported from `quasarr.search`
- `sources/` - see Child DOX Index

## Local Contracts

- Per-source gating before dispatch: hostname configured, category in `supported_categories`, category whitelist from `get_search_category_sources`, `supports_imdb` for the imdb branch, `supports_phrase` for the phrase branch, `supports_absolute_numbering` when an episode is given without a season, and `supports_date_numbering` for Sonarr's year + `MM/DD` episode shape. The feed branch checks only hostname/category/whitelist.
- Movie searches and feeds require a cached Radarr client; TV searches and feeds require a cached Sonarr client. Missing clients stop before source dispatch with an error. Book and music phrase searches have no Arr-client gate. IMDb searches warm the metadata cache from the category's required client before fan-out.
- Date-numbered requests are parsed once into a validated `datetime.date`; regular `season`/`episode` are cleared before dispatch and proven sources receive only `episode_date`. Invalid calendar dates stay on the normal numbering path.
- The method names `search` and `feed` are load-bearing - dispatch is `getattr(source, action)`.
- The fan-out is capped by a deadline: `get_search_results` takes an optional absolute `deadline` and otherwise starts one at `SEARCH_FANOUT_DEADLINE_SECONDS`. Callers running several searches for one *arr request must pass their own so the runs share it. IMDb metadata warming and source dispatch are both skipped once it has passed, and sources still running when it passes are badged and dropped from that response, so an *arr client never waits past its own request timeout. The pool is sized to one worker per dispatched source, otherwise the sources dispatched last would spend the deadline queued behind the first ones. Sources must still bound their own work - a dropped source contributes nothing.
- `SearchExecutor.run_all()` wraps every submitted callable in `search_runtime.source_task()` and reports only the fixed outcomes: `completed`/`errored`/`budget_exhausted` when a future is collected, `skipped` before submission when no deadline remains, and `dropped` for a still-running future at timeout. A dropped future is never collected or cached later; it owns one opaque overdue token, and its done callback resolves exactly that token once while discarding the late result.
- The same wrapper opens the request's cooperative budget with `use_search_budget(deadline, clock=self._clock)`, so every source runs under the fan-out's own absolute deadline and wall clock without any source method signature changing (see `sources/AGENTS.md` for what a source owes that budget). The callable never raises: it returns `_Completion(SourceTaskOutcome(results, budget_exhausted, error), at)`, because one shared future has to hold an outcome for every collector. `collect()` re-raises a carried error into its existing `except` branch, so a failure keeps one red/`errored` path. A budget-exhausted outcome is badged yellow, counted as `budget_exhausted`, still answered with - a partial result is better than none - and never cached. `SourceTaskOutcome` is module-private and is not re-exported; `run_all()` keeps its four-value return tuple.
- In-flight work is coalesced only by the exact integer key that `SearchExecutor.add()` already computes and passes to `SearchCache`; no source-, URL-, query-, or category-derived second key exists. The first submitter is the leader and submits the callable to its own executor. Followers share that `Future`, increment only the fixed `coalesced_waiters` counter, wait against their own absolute deadline, and never call `Future.cancel()`. Each follower calls `SharedWork.waiter_done()` in `finally` after result, exception, or timeout; it only decrements that flight's waiter count and cannot remove or cancel work.
- The leader future's done callback is the registry's sole removal path for success, empty success, exception, and cancellation. A joiner that sees a cancelled or otherwise done stale future takes leadership and replaces that map slot; callback cleanup is identity-checked, so the stale callback cannot remove the replacement flight. `SearchExecutor` keeps `shutdown(wait=False, cancel_futures=True)`; follower executors own no shared task, and the leader's one-worker-per-source pool means submitted work is already running rather than queued.
- Only an ordinary, complete release list that finished at or before the collecting request's own deadline is cached. The submitted callable returns one shared `_Completion(result, at)` envelope, so the timestamp is recorded *before* its future is marked done and every follower evaluates the same finish time against its own deadline. `Future.add_done_callback` cannot stamp it, because `set_result` wakes the `as_completed` waiter before it invokes callbacks. `_is_cacheable(future, completion, deadline)` remains the single eligibility gate and `collect()` remains the only cache writer; an eligible collector must also claim the flight's one cache write, allowing a later-deadline follower to cache when the leader timed out without duplicating writes when both are eligible. `as_completed` keeps a 0.1s floor under its timeout, so a result landing just past a request's deadline is still answered but never cached by that request. Exceptions are excluded by `collect()`'s own `except` branch, and a budget-exhausted result is excluded by the gate itself - it is a partial answer, so it must not be served for a whole TTL. A follower shares the leader's budget flag, because it shares the leader's one execution.
- `SearchExecutor` takes an injected `clock` (default `time.time`) and every wall-clock read in `run_all()` goes through it. It has to stay wall-clock, because the deadline is an absolute `time.time()` a caller hands in - `SearchRuntime`'s monotonic clock is a different domain and must not be used for it.
- `start_time` is taken before IMDb metadata warming: sources derive their own budget from it, so a later anchor would let them outlive the deadline by whatever the warming cost.
- Cache TTL is 300s for search, 60s for feed; the key nulls `start_time` and uses the cache-owner category. Cached entries skip execution entirely, so source methods must be safe to skip.
- `SearchCache` is bounded twice: at most `MAX_CACHE_ENTRIES` (2,048) entries and `MAX_CACHE_RELEASES` (50,000) retained releases, because entry count alone says nothing about size - one source can answer a broad query with thousands of releases. The bounds never shorten a TTL: an entry only leaves early when a limit is hit. `set()` removes expired entries first, replaces the key's own release accounting instead of adding to it, then evicts from the LRU front until both limits hold - so a write whose own release count exceeds the limit empties the cache rather than exceeding the bound. `get()` moves a live entry to the back, drops an expired one, and returns `(value, expires_at)` with `expires_at` an absolute wall-clock time, or `(None, 0)`. `sweep(now=None)` and `clear()` return how many entries they removed. The never-cache rules stay at the `collect()` call site.
- The cache owns the collection, not the caller: `set()` stores its own `list(value)` and `get()` returns a fresh `list` each time, so neither the list a caller wrote nor the list it got back can grow a retained entry behind the accounting and past the release bound. The releases inside are shared, not copied - the fan-out never mutates a release, and copying every dict on each read would cost more than the cache saves. Because the list is the cache's own, `len(entry.value)` is the release count and cannot drift from it.
- Cache counters go through the `quasarr.search.cache.search_runtime` name and are recorded outside the cache lock, so instrumentation can never make a reader wait on another subsystem's lock. `cache_hits`/`cache_misses` are recorded on every `get`; `cache_evictions` counts only limit-driven removals, because an expired entry leaving is normal and would otherwise hide a cache that is genuinely too small.
- Constructing `IdleMemoryReclaimer(search_cache, search_runtime)` is the explicit activation point; importing `quasarr.search` only re-exports it, so production enablement remains canary-gated. Once active, any request, source task, or overdue token cancels the pending timer, and a transition to all three gauges at zero arms one daemon pass after 30 quiet seconds. Each timer carries its arm-time activity generation; its callback identity-checks the token and generation while atomically claiming collection, then keeps checking that generation around every later stage. An arm stays provisional until `Timer.start()` returns: an idle schedule request that observes a published but unstarted timer is retained, so its owner either leaves the live arm in place or replaces a discarded arm with one fresh quiet-period timer. A callback that consumes its token but collides with a public collection or the 300-second limiter likewise defers or arms the appropriate successor. Factory/start failures record one pending schedule without recursively retrying; a later quiet schedule retries it, while a standalone public `collect_and_trim()` still performs directly and does not arm a timer without deferred work. Runtime transitions update gauges under a non-reentrant lock and invoke reclaimer callbacks only after releasing it, while timer threads start outside both runtime and reclaimer locks. Raising transition callbacks and normal timer scheduling/callback failures emit only fixed debug messages and cannot fail search work or leave a live token blocking later scheduling. The callback sweeps only expired cache entries, then runs cyclic GC on every platform and `malloc_trim(0)` only when a one-time `libc.so.6` probe on Linux exposes that glibc symbol. Any normal loader, symbol setup, or trim-call failure is a permanent process-local no-op, passes run at most once per 300 seconds, GC and trim run after cache, runtime, and reclaimer locks are released, and the quiet summary contains only fixed fields with PSS before/after - never a source, query, URL, category, hostname, title, or cache key.
- `tests/test_search_resource_load.py` is the automated, offline resource regression gate. It preserves production categories, eligible sources, 300-second search TTLs, and one-worker-per-source cardinality while exercising the real planner, executor, cache, singleflight, budget, and runtime owners. Its deliberately unbounded/no-budget/deadline-ignoring configuration must be rejected by the same `_bound_violations(...)` checker; the harness never constructs `IdleMemoryReclaimer`.
- The 24-hour rollout canary is operator-only, outside `unittest`, and not a merge gate. Keep every configured category and eligible source enabled and record aggregate snapshots only: no source initial or hostname, URL, query, title, category ID, cache key, credential, or other identifier. Acceptance is: p95 overdue-task drain <= 5 seconds after the response deadline (record outliers, do not assert them); deadline drops reduced by >= 75% for the same request sequence (<= 41 against the sampled 166); Quasarr anonymous PSS <= 559,356 KiB (about 546 MiB) after 10 idle minutes; search p95 regression <= 10%; and all configured categories and eligible sources preserved. If PSS fails while cache counts and active/overdue tasks are zero, stop and design a recyclable search worker; do not reduce categories or TTLs ad hoc.
- The FlareSolverr operating profile is a separate operator-only gate. Prerequisite: rotate any deployment-management credential exposed while investigating this issue. Then set only `MAX_SESSIONS=6`, `SESSION_IDLE_TIMEOUT_MINUTES=2`, `SESSION_MAX_LIFETIME_MINUTES=15`, and `SESSION_REAPER_INTERVAL_SECONDS=30`; change environment values only, never FlareSolverr source. Verify zero sessions within three idle minutes and working set below 1 GiB within four minutes, and roll back those variables if browser success rate regresses. Do not change JDownloader. The deferred Playwright prototype contributes nothing to this branch or either gate.
- Per-source results are merged, date-sorted descending, title-filtered by `release_matches_search_category`, then offset/limit-sliced; feed responses are never paginated.
- Search sources normally have a same-key download twin (FX is the search-only exception); the `source_key` embedded in the search payload routes the later `download()` call to the same-key twin first when one exists.
- `runtime.py` counters are process-local and fixed-cardinality: `snapshot()` returns exactly the documented counter keys plus `rss_kib`/`pss_kib`/`threads`. Never add a source initial, query, URL, hostname, or category ID to a counter name or value - the snapshot is meant for logs, so every key and value must stay bounded. `record_source_outcome()` accepts only `completed`, `dropped`, `skipped`, `errored`, and `budget_exhausted` and raises `ValueError` otherwise.
- `SearchRuntime` takes an injected `clock` and `memory_reader` so tests stay deterministic; gauges (`active_requests`, `active_source_tasks`) are decremented in `finally`, so a raising body still returns them to zero. `snapshot()` never raises and never widens its value types: a `memory_reader` that raises, returns a non-mapping, or yields a non-`int` value degrades that field to `None`, so `rss_kib`/`pss_kib`/`threads` are always `int` or `None`. `read_process_memory()` reads `/proc/self/status` and `/proc/self/smaps_rollup` and returns `None` readings on non-Linux hosts or when a file is missing - it never raises into a search request.
- Overdue accounting is token-owned: `mark_source_overdue()` returns an opaque token and `resolve_source_overdue(token)` releases exactly that token once, returning `False` for a replayed, stale, or foreign token, so a late future can never resolve another task's mark. The gauge is the number of held tokens and therefore cannot go negative. There is deliberately no public `reset()` - zeroing counters while another thread sits inside `request()`/`source_task()` would let that thread's `finally` decrement a gauge below zero; tests build their own `SearchRuntime` or patch the `search_runtime` singleton instead.
