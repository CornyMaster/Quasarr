# quasarr/api/ - HTTP Surface

## Purpose

The single Bottle app serving (1) the Newznab-indexer and SABnzbd-client emulation consumed by the *arr apps, (2) the browser web UI, (3) the JSON config endpoints behind that UI, and (4) the SponsorsHelper companion API. `get_api()` is the main process's blocking entrypoint, called from `quasarr/__init__.py` after the helper workers are spawned as daemon processes.

## Ownership

Submodules are packages, each with its routes in `__init__.py`: `arr/` (emulation core), `captcha/` (userscript-based CAPTCHA pages and the quick-transfer return path), `config/` (settings endpoints), `jdownloader/` (page-fragment helpers, registers no routes), `packages/` (package list UI; `packages/carbon.py` is the Carbon Downloads data-contract projection - models/row builders only, no routes), `sponsors_helper/`, `statistics/`.

`api/jdownloader/get_jdownloader_disconnected_page(shared_state, back_url="/")` dispatches Classic/Carbon via `page_dispatch.render_page`; the Classic branch is the original body unchanged, the Carbon branch renders a centred `cds-page--narrow` column (eyebrow "JDownloader", title "Connection required") via a lazy `carbon_templates` import: an error notification, the device status through the shared `status()` helper in `cds-mono` (falling back to the label "JDownloader" when no device has ever been configured, so an empty `device_name` never renders as a bare colored dot with no label), and two actions - "Open JDownloader settings" (primary, `href="/settings"`) and "Retry now" (tertiary, `data-action="jd-retry"`, wired in `carbon.js`'s `bootstrapCarbonStatusPages` IIFE to reload the page) - `back_url` is unused on the Carbon branch. Both `captcha/__init__.py` and `packages/__init__.py` call this shared function unmodified, so they inherit Carbon support without either file being touched.

## Local Contracts

- Each route submodule exposes one setup function taking the Bottle app (or app + shared_state), wired into `get_api()` in `quasarr/api/__init__.py` (`jdownloader/` is the exception: a helper module with no routes and no setup function). The auth routes and auth hook must be installed before any route module registers.
- Auth is enforced structurally: every route under `/api`, `/download/`, or `/sponsors_helper/api/` must carry `@require_api_key`, or the startup call `audit_route_auth_modes(...)` raises `RuntimeError` and the app will not start. Routes ending in `.user.js` are public by whitelist. Everything else defaults to browser auth, which is a no-op unless `USER` and `PASS` env vars are set.
- UI preference routes: `GET /ui/<mode>` is browser-auth, validates mode against `VALID_UI_MODES`, writes cookie via `response.set_cookie(..., path="/", httponly=True, samesite="Lax")`, and redirects only to sanitized relative `next` targets. `POST /api/ui-preference` is API-key-auth, must return exact `400 {"success": false, "message": "Invalid UI mode"}` for malformed JSON, non-object JSON, missing mode, or invalid mode, and only persists on valid mode.
- Carbon browser dispatch: `/`, `/settings`, `/packages`, `/statistics`, `/hostnames`, `/categories`, and the six provider CAPTCHA pages are thin `render_page(...)` callbacks. Their existing bodies live unchanged in private nested `_classic_*` callables. Carbon imports stay inside the callback-local `carbon()` function so a missing or broken view module can always recover to Classic. `api.statistics.carbon.render_statistics(shared_state)` is implemented: it renders the same 37 `StatsHelper.get_stats()` values as `_classic_statistics` - four top KPI metric tiles (Download attempts, CAPTCHA decryptions, Packages downloaded, Failed downloads) plus five detail tiles (CAPTCHA decryptions ratio bars, Cached metadata, Linkcrypter blocks, Filecrypt cohort, Terminal operations) in one self-arranging `.cds-grid--auto` grid (`repeat(auto-fit, minmax(300px, 1fr))`, `align-items: stretch` so same-row tiles share a height) - via `carbon_templates.grid`/`tile`/`kv_rows`/`metric_tile`; the Filecrypt cohort's live sweep state renders through the shared `status()` dot rather than a tag, the sweep deadline as `<time data-epoch>`, and no value is renamed, dropped, or recomputed. Its four top KPI tiles render inside a `.cds-kpi-row` grid wrapper (`carbon.css`, 4/2/1 columns at the existing 1056px/672px breakpoints). Every Carbon view's `render_carbon_html(..., captcha_count=...)` argument should come from the shared `carbon_templates.protected_captcha_count(shared_state)` helper (hoisted off this module's former private `_captcha_count`) rather than a private per-view copy. `api.carbon.render_dashboard(shared_state)`/`render_settings(shared_state)` are implemented: each delegates to a pure model builder (`build_dashboard_model`/`build_settings_model`) that reads only `shared_state.values`, `Config`, and `DataBase` - never `shared_state.get_device()` or `downloads.packages.get_packages()` - so page construction, including a HEAD `/` (Bottle answers HEAD by running the same GET callback and discarding the body), never blocks on JDownloader. The Dashboard's top-three-downloads tile ships as an empty `#dashboard-queue-content` placeholder and is populated client-side from `GET /api/packages/list` (the shared packages-list data contract) after first paint, with an isolated unavailable message scoped to that one tile on error/timeout/disconnect - the page shell always completes independent of JD state. Settings renders Appearance (a client-only theme `<select data-action="theme-select">`), JDownloader, API & Timeouts, Link Protection (a two-option `defer`/`fail` segmented radio, cooldown hours, and the Filecrypt sweep window with its stored/environment/default source tag and "Use Docker/default value" checkbox, saved together through the existing `/api/crypter-block/settings`), FlareSolverr, Notifications (Discord and Telegram cards, each rendering its own real configured credential value into `value=` like every other Settings field - `_h(settings.get("discord_webhook"/"telegram_bot_token"/"telegram_chat_id", ""))` fed by the cached `notification_settings` - each with its own Send Test, but one unified section-wide Save), and *arr sections. Every external-JS save in `carbon.js`'s second (`bootstrapCarbonDashboardAndSettings`) IIFE fetches the matching authenticated `GET` endpoint immediately before POSTing. Notifications' single `buildNotificationsPayload()`/`saveNotifications()` reads every rendered credential field for both providers unconditionally (no per-provider branching) so one Save can never silently discard a typed edit anywhere in the section - an earlier per-provider-scoped save read only the DOM field of the provider being saved and discarded an edit typed into the other provider's field while still reporting success; each provider's own Send Test still saves (via the same unified `saveNotifications()`) before testing. The pre-save fetch still matters for the toggle/silent maps: each is merged onto the fetched object so a case this page's static `notificationCaseKeys()` list does not know about is never dropped, for either provider. Radarr/Sonarr saves fall back to the fetched `api_key` when the field is left blank (an untouched key survives a URL-only edit), while a dedicated Clear action sends an explicit empty pair, bypassing the merge, so intentional clearing still works. Clear never fires straight off its click: it first opens a confirmation modal (eyebrow the "*arr clients" tile heading, secondary Cancel left, danger Clear right) matching the confirm-then-act anatomy "Restart Quasarr" and "Delete package and files" already use, and only the confirm button's `data-action` (`radarr-clear-confirm`/`sonarr-clear-confirm`) closes the modal and calls the unchanged clearing request. FlareSolverr's single URL field has no merge - a blank submission is the existing intentional clear-and-skip action, matching Classic. `api.packages.carbon.render_downloads(shared_state)` is implemented: it renders only the page-level notices (the slow-connection warning and the `deleted=1`/`deleted=0` status banner mirrored from the existing `/packages/delete/<id>` redirect route) and an empty loading skeleton for the A1 deferred table (selection/release/state/evidence/next check/sweep progress/actions columns, the action column unlabelled like Queue's and History's, bulk toolbar disabled at zero selection), Queue, History, and a collapsible Other-packages section. The release filter (`#downloads-search`, placeholder "Search releases") lives in the Queue tile's own `.cds-tile__head-row` beside the live `Queue (n)` count: it sits inside `#downloads-content`, which is safe because every refresh clears a `<tbody>` and never a whole tile or the container, so a typed value and the input's focus survive each poll. `applySearchFilter()` reads that one input and re-applies the filter to `#downloads-content tbody tr[data-package-name]` after every rebuild - it never touches `shared_state.get_device()`/`get_db()` itself. Every row for all four sections is built client-side in `carbon.js`'s third IIFE (`bootstrapCarbonDownloads`) from `GET /api/packages/list` (the shared packages-list data contract) on load and every 5 seconds after, the same house pattern `api.carbon._dashboard_queue_tile()`/`loadDashboardQueue()` established for the Dashboard queue preview - there is exactly one row-rendering implementation (JS), never a server-rendered duplicate. `carbon.js`'s `clearDeletedQueryParamAndScheduleBannerHide()` strips `deleted=` from the URL via `history.replaceState` and auto-hides the banner after 5 seconds, matching Classic's own inline-script handling. A shared `bootstrapCarbonTime` IIFE (`window.CarbonTime`) owns the one countdown parser/updater `deferredCountdownEpoch(element)` (`element.dataset.cohortDeadlineEpoch ?? element.dataset.retryAfterEpoch`) that both `data-retry-after-epoch` and `data-cohort-deadline-epoch` `<time class="deferred-countdown">` elements go through, plus `upgradeEpochTimes()`, which upgrades every OTHER `<time data-epoch>` element (currently only the Statistics page's Filecrypt sweep deadline, unchanged Python-side) from a fixed UTC string to local time plus a relative phrase, run on `DOMContentLoaded` and every 30s on every Carbon page. D1 wording: ordinary queue/history deletion still navigates to the existing `/packages/delete/<id>` redirect route (`confirmDeletePackage()`, a real `<button type="button">` confirm control - not an `<a>` without `href`, which the shell's `getFocusable()` never selects and Enter/Space cannot activate - "Delete package and files", naming disk deletion and irreversibility); deferred pending-row removal calls the existing `/api/packages/deferred` DELETE route (`confirmRemovePending()`, "Remove pending package(s)", no disk/irreversibility wording, no `records_only`). Row and bulk actions come in two shapes, chosen by how often the control repeats and how obvious it is. The queue/history delete and the deferred row's CAPTCHA link are icon buttons (`.cds-icon-button`, `.cds-row-actions` for gap/alignment and a scoped hover/sizing override so the header's dark-background hover tint never leaks into a light table row, `.cds-icon-button--danger` for destructive ones, built by `buildActionButton()`/`buildCaptchaLink()`); the deferred row's own Check and Remove are labelled `cds-btn cds-btn--ghost cds-btn--compact` / `cds-btn cds-btn--danger-ghost cds-btn--compact` buttons built by `buildTextActionButton()`, whose visible word comes from the closed `buttonTextForAction()` map. Either shape sets `aria-label` and `title` to the same package-naming string, so the labelled buttons read "Check"/"Remove" on screen and "Check now: <release>"/"Remove pending package: <release>" to a screen reader - the visible words are contained in the accessible name, satisfying label-in-name. `trash-can`/`renew`/`unlocked` were added to `carbon_icons.py` (sourced from the Carbon repo, sha256 recorded) for the bulk toolbar's server-rendered icon+text buttons; only `trash-can` and `unlocked` are also mirrored as fixed, non-interpolated markup client-side (`buildActionIcon()`, parsed via a detached wrapper's `innerHTML` rather than `createElementNS()` - the SVG namespace URI createElementNS() needs is itself a web-address-shaped string literal this file's no-remote-URL contract forbids) since `render_icon()` only runs server-side. Icon-only buttons' `aria-label` (their whole accessible name) and `title` are both set to the same string leading with the fixed action phrase (e.g. `"Delete package and files: <name>"`), matching label-in-name (WCAG 2.5.3). Selection is snapshotted via `selectedDeferredPackageIds()` (`.deferred-select:checked` -> `checkbox.value`) immediately before the deferred tbody is replaced (inside `renderDeferredTable()`, not before the fetch that produced the new rows - that earlier snapshot point widened the race window on a slow connection) and restored via `restoreDeferredSelection()`'s `Set.has(checkbox.value)` guard - never a selector built from package data. The Other-packages summary count (`updateOtherSummary()`) is rebuilt from `lastOtherTotal` via DOM nodes on every render, never a bare `summary.textContent = <string>` assignment - that used to destroy the `#downloads-other-count` span permanently after the first poll. Destructive actions pause the 5s poll (`pauseRefresh()`) before `window.showModal(...)` and resume via a `MutationObserver` on `#cds-modal`'s `hidden` attribute (`installModalResumeHook()`) - the base shell's Cancel/Escape/backdrop-close paths all call its own private `closeModalInternal()` directly, never the exported `window.closeModal()`, so the attribute is the only path-independent close signal. `render_downloads()` also prepends a `<noscript>` warning notice pointing at `/ui/classic?next=/packages` - every row of every section on this page is populated client-side, so a JS-disabled visitor previously got a silent empty shell with no indication anything was wrong. `carbon.css`'s `.cds-table--sticky-col` pins both the checkbox column (`th`/`td:first-child`) and the release column (`nth-child(2)`) under 672px - only the release column used to get `position: sticky`, so the checkbox column scrolled out from under it, leaving its reserved 40px gap unpinned. Classic `/settings` redirects to `/`; `/captcha` remains only the provider redirect dispatcher.
- `api.config.carbon.render_hostnames(shared_state)`/`render_categories(shared_state)` are implemented. Hostnames delegates to `build_hostnames_model()`, a thin wrapper around `storage.setup.hostnames.build_hostname_rows()` (the shared hostnames data layer) plus the stored import URL and FlareSolverr-skipped flag - it never re-derives row status/capability logic, and renders every row `build_hostname_rows()` returns (no fixed-size sample). The uncontrolled `details` field (exception text that can embed a configured source hostname) is deliberately never written into the initial page HTML or any data attribute: `carbon.js` fetches it fresh from the existing authenticated `GET /api/hostnames` only when a row's status modal is opened, and renders it solely as a text node inside that modal. Stored user/password credential values never reach this page at all - the credentials section (shown only when a row `supports_login`) always renders blank inputs and posts through the existing `POST /api/hostnames/check-credentials/<shorthand>`. Saving hostnames stays a real `<form action="/api/hostnames" method="post">` submission (a confirmation modal fronts the same existing navigation) because that endpoint reads `request.forms` and answers a full HTML reconnect/fail page, not JSON - the endpoint and its payload shape are unchanged. Categories delegates to `build_categories_model()`, ported from `_classic_categories`'s exact default/custom/subcategory grouping and selectable-base-type rules over `storage.categories`; mirror-priority editing and search-source selection are Carbon modals that still call the existing `POST /api/categories/<name>/mirrors` and `POST /api/categories_search/<cat_id>/search_sources` endpoints with unchanged payload shapes (an empty search-source selection is sent as `[]`, meaning "all hostnames", never a synthetic full list). Both views' interactive elements are real `<button>`/`<a>`/`<input>`/`<select>` nodes (never a bare `<div data-action>`) so the shared `#cds-modal` host's existing focus-trap/Escape/return-focus behavior covers every dialog by keyboard with no page-specific work. `.cds-hostname-row__skip-banner` (the "Login was skipped..." note) used to set `color: var(--cds-support-warning)` directly on the page background - measured contrast 1.5-1.7:1 in light theme, far below WCAG AA's 4.5:1. Fixed to the same warning-tinted-background-plus-default-text pattern `.cds-notification--warning`/`.cds-hostname-credentials__warning` already use (dark text on `--cds-notification-warning-bg`, 17:1 light / 10.6:1 dark): the same "warning yellow always uses dark text" rule applies to every such usage, not only full notification blocks. Both mirror/search-source modal row builders (`buildMirrorRow`/`buildSourcePill` in `carbon.js`) build their rows as DOM nodes offscreen and hand `body.innerHTML` (a STRING) to `showModal()`; a checkbox's `checked` PROPERTY never serializes into that string, so any such builder must also set the `checked` ATTRIBUTE (`checkbox.setAttribute('checked', '')`) or every previously saved selection silently renders unchecked after Edit, and an untouched Save then re-persists a wiped whitelist - a Critical defect found and fixed after the Hostnames/Categories views shipped; the same audit found no other `.checked=`/`.value=`/`.selected=` site feeding an innerHTML string this way. The mirror row's tier-1 marker is the existing `.cds-tag` component (`Recommended`), never a bare emoji glyph, and its reorder buttons use the `arrow--up`/`arrow--down` `carbon_icons.py` entries (sourced from the same upstream repo, sha256 recorded, mirrored client-side as fixed markup exactly like the Downloads row-action icons) instead of `↑`/`↓` text glyphs - `tests/test_carbon_templates.py` scans the whole of `carbon.js` for emoji/dingbat/arrow-glyph code points so a JS-built equivalent can't reintroduce either. The one permitted codepoint is U+2192 RIGHTWARDS ARROW, and only because it is typography inside a link label rather than a control drawn as a character: the queue row's inline "Solve CAPTCHA →" matches the server-rendered "Solve CAPTCHA →"/"Statistics →" link actions this module already ships. Every other arrow in the same block stays forbidden, so reorder controls can still never be glyphs. `.cds-modal__surface` caps at `max-height: calc(100vh - 32px)` and is a flex column whose `.cds-modal__body` scrolls (`overflow-y: auto; min-height: 0`) while `.cds-modal__header`/`.cds-modal__actions` stay fixed (`flex: 0 0 auto`) - without it a modal taller than the viewport (the real 23-entry `SHARE_HOSTERS` mirror list) clipped both its header and its Save/Cancel actions with nothing scrollable, confirmed live before the fix. Below 1056px `.cds-hostname-table`'s own `overflow-x: auto` container also carries a right-edge scroll-shadow `background-image` (a "cover" layer on `background-attachment: local`, anchored to the scrolled content's trailing edge, over a "shadow" layer on `background-attachment: scroll`, fixed to the visible edge) so a narrow viewport has a visible cue that the Capabilities column - otherwise clipped off-canvas with no affordance - can be reached by swiping; the shadow layer disappears once scrolled to the end. The row/head markup and the pinned `min-width: 760px` scroll-container contract are unchanged. `_hostname_row_html()` (this module) is the single dense hostname-table row renderer - code, `status()` dot, hostname input, capability chips - shared verbatim by this page and the setup wizard's Hostnames step (`quasarr/storage/setup/carbon.py::_setup_hostname_row_html`, which used to keep its own duplicated markup); the pages differ only in parameters passed to the same call (this page's status opens a JS-fetched modal via `status(as_button=True)`, the setup page's status is inert with a separate Details toggle button instead). Both call `status(..., dot_only=True)`: the row shows only the coloured dot (a 24x24 `cds-status--dot-only` hit area around the 10px dot), with the status text moved into a `title` attribute for hover and a `cds-visually-hidden` text node for assistive technology - never colour alone. `carbon.js`'s `checkSetupHostnameCredentials()` rebuilds that same dot-only shape in place after a successful check.
- Presentation conventions shared across every Carbon page in this package: `carbon_templates.grid(children, variant)` maps `variant` to a fixed CSS class - `dashboard` (`.cds-grid--dashboard`, the Dashboard's queue-tile-plus-stacked-sidebar two-column layout), `settings` (`.cds-grid--settings`, Settings' own dense `columns: 380px` tile layout - short tiles stack under short tiles instead of leaving dead space under a fixed-row grid, each tile keeping `break-inside: avoid` and its own 16px bottom margin), `2`/`3` (`.cds-grid--2`/`.cds-grid--3`, Categories' side-by-side detail-tile grids and Settings' own two-field rows - `.cds-grid--2`'s fields subgrid across two explicit row tracks so a wrapped label never shifts its input out of line with its neighbor's), `auto` (`.cds-grid--auto`, Statistics' single self-arranging detail-tile grid), and `stack` (`.cds-stack`, a 16px-gap vertical stack for tiles or dialog sections that carry no margin of their own - the Dashboard's API/summary pairing, the CAPTCHA page's tile stack). A live, mutable state renders through the shared `status()` dot (Queue rows, Hostnames status, the CAPTCHA/JDownloader-disconnected device status, the Filecrypt cohort's sweep state on Statistics); a closed classification renders through `tag()`/`.cds-tag` instead - download category and History's finished result on Downloads, the Hostnames mirror tier's "Recommended" marker, and Hostnames' capability chips (language/invite/login/account/FlareSolverr) - the two vocabularies are never interchanged. Button weight follows one rule everywhere a tile carries actions: at most one filled `.cds-btn--primary` per tile/section; `.cds-btn--secondary` is reserved for a confirmation modal's paired Cancel-plus-confirm footer and is never a second same-tile fill (Settings renders none at all); a repeatable non-primary action (Verify credentials, Send test, Regenerate) uses `.cds-btn--tertiary`; destructive actions use `.cds-btn--danger`/`.cds-btn--danger-ghost`.
- `api.captcha.carbon.render_captcha(shared_state, provider)` is implemented for all six protected-provider pages (`hide`, `junkies`, `he`, `keeplinks`, `tolink`, `filecrypt`); `/captcha` itself is untouched and stays the Classic-only redirect dispatcher, and Hide renders through the identical unified path as the other five rather than gaining any bespoke handling. The page never solves a CAPTCHA server-side - it only re-skins the existing browser/userscript flow. It renders as a centred 720px `cds-page--narrow` column: eyebrow "Link protection", title "Solve CAPTCHA" with the release name as its page-header subtitle (the document `<title>` stays the per-provider `<Provider> CAPTCHA`, since a single queued package renders no selector and the subtitle is then the only on-page place the release name appears), an inline info notification (`cds-notification--inline`), then `grid(..., "stack")` - the shared 16px-gap helper, needed because `.cds-tile` carries no margin of its own - around: one tile holding the package selector plus a `cds-meta` line (`Crypter: <provider> · Mirror: <netloc of the first link> · Links: <count>` - the mirror is always computed live from the payload's own link via `urlsplit`, never a hardcoded value), the hidden failed-attempts warning (its own Delete Package action is `cds-btn--danger-ghost`, matching every other destructive control on this page), a tile with a 48px primary CTA (`cds-btn--cta`) plus a secondary source-page CTA plus a helper line rendered as a `cds-text-link` that points at the exact same `captcha-reset-tutorial` action/storage key as the Reset Setup Guide button beside it - reopening the real tutorial, never `captcha-open`, which would silently navigate straight to the provider once `tutorialSeen()` is true - and a "Manual submission" tile. A danger-ghost delete action sits below the stack. The "Back" button is the one control this design drops. It preserves byte-for-byte: the `/captcha/<provider>.user.js` route, the quick-transfer query contract (`transfer_url`/`pkg_id`/`pkg_title`/`pkg_pass`, plus Junkies' `jk_user`/`jk_pass` when `Config("JUNKIES")` holds credentials) appended to the first prioritized link exactly like Classic's `render_userscript_section`, the base64 `<captcha_type>|<encoded_payload>` package-selector option contract (now labeled "Package · N waiting" and styled `cds-mono`), the `/captcha/bypass-submit` manual form's exact action/method/enctype and `package_id`/`title`/`password`/`links` field names, and the `captcha_attempts_<package_id>` localStorage counter key. `check_package_exists(package_id)` (imported from this package's `__init__.py`) dispatches Classic/Carbon via `page_dispatch.render_page`: the 404 status and the "Package not found or already solved." message are identical under both UIs, but the body markup is the Classic literal under Classic and `carbon_templates.render_carbon_error_page` under Carbon - the Classic branch is byte-for-byte the pre-wiring literal, unreachable through `render_error_page`'s own dispatcher since this call site builds its own `HTTPResponse` rather than routing through it (`response.status` is a no-op on an already-raised `HTTPResponse`, so status lives on the constructed object itself). HE's missing/`None` password is coerced to `""` before rendering, matching Classic's HE-specific guard. Tutorial timing, first-use storage, reset, package-selector navigation, manual-submit wiring, and the delete action move into `carbon.js`'s third (`bootstrapCarbonCaptcha`) IIFE behind delegated `data-action` handlers (`captcha-open`, `captcha-reset-tutorial`, `captcha-open-source`, `captcha-reload`, `captcha-package-select`, `captcha-manual-submit`, `package-delete` - the last navigates to the button's own `data-href`, the same `_delete_url()` value Classic already used) - the first-time-setup tutorial copy (including the external Tampermonkey link) is pre-rendered server-side into a hidden `#captcha-tutorial-content` container and only read out by `openProvider()`, so carbon.js itself never embeds a URL literal (a repo-wide static-file structural pin `test_carbon_templates.py` already enforces). Three window-scoped compatibility functions are preserved from Classic's inline equivalents: `window.incrementCaptchaAttempts`/`getCaptchaAttempts`/`clearCaptchaAttempts`, all package-scoped via a `data-package-id` attribute on the page's `.cds-captcha-page` wrapper. `carbon.css` gained `.cds-captcha-actions` (a small flex button-row), `.cds-manual-submit-body`/`[data-manual-submit] > summary` for the collapsible manual-submission section, `.cds-meta` for the package tile's crypter/mirror/link-count line, and `.cds-text-link` (a button reset to a plain underlined inline link - the shape the helper line needs, not previously available since every existing `.cds-btn` variant is chip-shaped); every other element reuses the existing `.cds-field`/`.cds-field__select`/`.cds-field__textarea`/`.cds-btn`/`.cds-notification`/`.cds-stack` component classes rather than adding new ones. `openProvider()` no longer navigates this page away: `openProviderWindow(url)` opens the provider in a named popup (`quasarrCaptchaProvider`, `popup=yes,width=1180,height=920`, deliberately without `noopener` - the outcome page needs `window.opener`), counts the attempt, and falls back to the former same-window navigation only when the popup is blocked, so a blocker cannot strand a visitor mid-solve. The three routes a solve ends on - `GET /captcha/quick-transfer`, `GET /captcha/delete/<package_id>` and `POST /captcha/bypass-submit` - dispatch through `page_dispatch.render_page` via the module-level `_render_captcha_outcome(page_id, classic_fn, *, status, heading, message, package_id, rows, actions)` helper; every Classic body is byte-for-byte the one it always rendered (the four `except ... as e` handlers bind `failure_detail = str(e)` first, since the name is unbound once the handler exits and the body is now rendered from a lambda), and the Carbon branch renders `api.captcha.carbon.render_outcome(...)` - a standalone `render_carbon_simple_page` status card carrying `data-captcha-result` (`success`/`warning`/`error`) and `data-package-id`, an eyebrow/title pair, a matching notification, `kv_rows` details, and a `cds-cta-row` whose "Close window" button ships `hidden`. `carbon.js`'s `bootstrapCarbonCaptchaResult` IIFE reads those two attributes on load: it clears the spent `captcha_attempts_<package_id>` key (Classic does this with an inline `<script>`, which the Carbon CSP forbids), reveals the Close button only when `window.opener` is a live same-origin window, and reloads that opener on a `success` result so the queue behind the popup stops offering the package that was just solved. `carbon.css` gained `.cds-status-card .cds-kv__value { overflow-wrap: anywhere; text-align: right }` - a release name is one unbroken token and would otherwise run past the 440px card.
- `save_flaresolverr_url()` (`quasarr/storage/setup/flaresolverr.py`) gained an additive JSON response branch consumed by Carbon Settings: a request whose `Content-Type` is exactly `application/json` gets `{success, message}` back (same validation, same persistence, same side effects) instead of the HTML reconnect/fail page; the exact existing form-encoded branch (Classic UI, first-run setup, both keyed off `request.forms`) is untouched. The no-module-scope-`.carbon`-import rule applies to every route-owner module as a whole, so a broken or incomplete Carbon submodule can never block the rest of the file from registering its routes: `quasarr/api/packages/__init__.py` imports `api.packages.carbon` lazily inside the `/packages` page's `carbon()` callback and, separately, inside the JSON `/api/packages/list` route below (that route has no Classic fallback of its own - a broken `carbon.py` fails that one request, not module import).
- `GET /api/packages/list` (`@require_api_key`) returns the Carbon Downloads data contract: `PackageListResponse {connected, linkgrabber, deferred, queue, history, other_queue, other_history}` built by `api.packages.carbon.build_package_list_response()`/`empty_package_list_response()`. The route reads `shared_state.values.get("device")` exactly once - absent returns the empty `connected: false` shape without calling `build_package_list_response()`; present calls only `downloads.packages.get_packages_for_device(shared_state, device)`, never `shared_state.get_device()`. `api/packages/carbon.py` owns the projection (row builders for `QueueRow`/`HistoryRow`/`DeferredRow`) and never emits a protected URL, source hostname, sweep/offer/operation ID, or link fingerprint - only the exact schema fields; `HistoryRow.error` additionally passes through `_scrub_protected_links()` before it enters the row, since a raw exception message reaching the legacy `failed` DB is not guaranteed URL-free. `GET /api/packages/content` and `_render_packages_content()` stay untouched by this contract; the two rendering paths do not share code.
- `DeferredRow.state`'s `"retest"` value is reserved: it stays a valid, accepted schema/enum value (`carbon.DEFERRED_STATE_VALUES`), but `carbon._deferred_state()` never emits it and no route or helper here still reads a live `retest_members` set. Reason: `crypter_sweeps.decision_snapshot()`'s `retest_members` is non-empty only for a `healthy`/`individual` decision, and `_legacy_shaped_snapshot()` maps that to legacy state `"available"` (`retry_after_epoch: 0`) - so `hold_type == "crypter_cooldown"` (which requires legacy state `"cooldown"`) and a non-empty retest queue can never both be true within one consistent read of the same row. An earlier revision derived `"retest"` from a *second*, independently-timed `crypter_projection()` read alongside `get_packages_for_device()`'s own read; that second read could observe a `cooldown -> healthy` transition the first read had not yet seen, producing an internally contradictory row (`state: "retest"` next to `cohort_retest_depth: 0`) that could flicker between requests - violating the same-row-read invariant `downloads/packages/__init__.py::project_package_defer()` documents (a transition between two reads can never be projected half-applied). Removed for that reason. `cohort_retest_depth` remains the crypter-wide count `DeferredRow` surfaces for a "Retest queue: N" display, matching Classic. **For future work**: `"retest"` becomes reachable only once a genuine per-package fact can be derived from a *single* consistent row read (not a second independently-timed one) - the same precedent applies to any other field this contract adds: a schema value must be derivable from a per-package fact within one read, never copied identically from a shared crypter-wide snapshot onto every held package, and never assembled from two reads that can observe different moments of live state.
- SABnzbd emulation (`GET/POST /api` with `?mode=`): responses mimic SABnzbd JSON; Quasarr package IDs are surfaced as `nzo_ids`; `get_cats` keeps `*` as the first category; `get_config` returns `misc.quasarr=True` so the *arrs can detect Quasarr; queue/history embed a nonstandard `linkgrabber` object; failures add `quasarr_error: True`.
- SABnzbd add responses log a persisted failed package at WARN; a malformed download result without a package ID logs at ERROR.
- Newznab emulation (`GET /api` with `?t=`): movie/tv searches (`t=movie`, `t=tvsearch`) are imdbid-only (q-only requests are deliberately ignored, except q-as-episode alongside an imdbid) and require configured Radarr/Sonarr clients respectively; `t=book`/`t=music` search by author/title phrase; `t=search` is honored only for magazarr/lidarr User-Agents; RSS titles are prefixed `[<XY>]` except for magazarr; enclosures use type `application/x-nzb`; a placeholder "No results found" item is returned when neither imdbid nor q is present and the search produced no items - it keeps *arr connectivity tests passing. Each non-empty release link owns one durable first-seen `pubDate` in `newznab_publication_dates`, keyed only by the SHA-256 of that link: repeated searches and restarts therefore preserve Radarr/Sonarr blocklist identity even when a source supplies a moving fallback date. RFC-822 and ISO-8601 inputs are normalized to UTC RFC-822 before use or persistence; parse, timezone conversion, and formatting failures (including date overflow), malformed source or stored values, and non-string values all fall back to the request timestamp (or the fixed safe epoch if that too is invalid), and an invalid stored row self-heals in the same atomic mutation. Every result is processed in bounded write batches with no total-result cap; a storage outage logs only the exception class and serves the canonical source/fallback date rather than failing the search.
- The fake-NZB roundtrip: search results embed `/download/?payload=...`; `GET /download/` renders `<nzb><file title url size_mb password imdb_id source_key/></nzb>` (the free-text `title`/`url`/`password` attributes are XML-escaped via `_xml_attr`, so source-specific characters like `&` in hoster URLs or accents in French titles do not corrupt the NZB); the *arr app posts that file back via `POST /api` (multipart field `name`) or `mode=addurl`, and both paths decode the same payload and call `quasarr.downloads.download()`. The payload format is owned by `providers/utils.py` (`generate_download_link`/`parse_payload`).
- Client identity comes exclusively from the User-Agent header (`extract_client_type` and the category resolvers in `providers/utils.py`).
- A search request computes one `SEARCH_FANOUT_DEADLINE_SECONDS` deadline and passes it into every `get_search_results` call it makes. Cache-sharing categories run sequentially, so a per-call deadline would let a multi-category request take a multiple of what the *arr client waits.
- One Newznab search-mode request opens exactly one `search_runtime.request()` scope after category/cache-family planning and around the shared mode dispatch, including supported modes that produce no releases. Request exit logs one fixed-cardinality `Search runtime summary` containing only snapshot deltas and current RSS/PSS/thread readings; queries, source initials, category IDs, cache keys, URLs, and hostnames never enter that summary.
- Every successful CAPTCHA flow ends in `downloads.submit_final_download_urls(..., remove_protected=True, notification_details=...)` and increments the matching `StatsHelper` counters; manual flows identify their solution method and SponsorsHelper passes solver details. Terminal submission failures increment failed counters and update the same tracked release notification. SponsorsHelper disable persists the advanced notification case/silence state so a later manual solution evaluates the next transition correctly.
- Download-category mirror-whitelist order is also the protected-link priority order: the config UI preserves and reorders that ranking, and both the manual CAPTCHA redirect and SponsorsHelper package handoff sort candidate links by it. Categories without a mirror whitelist retain the legacy Rapidgator-first fallback.
- SponsorsHelper routes use trailing slashes; most require an active helper (HTTP 402 otherwise), tracked via `helper_last_seen` with a 300s timeout; `POST to_decrypt/` requires the helper's `supported_urls` and only hands out packages matching its URL patterns or optional `supported_mirrors`. Helpers advertising the exact, case-sensitive `crypter_defer_v1` capability skip only supported links under an active crypter cooldown or matching package hold, retain alternate crypters and later packages, and atomically consume a queued probe only when the selected link still needs it. Only the first 100 unique, syntactically valid `excluded_package_ids` are honored, where validity is exactly `constants.PACKAGE_ID_PATTERN` - the same check that `select_helper_package(enforce_package_contract=True)` applies to every candidate row for a capable helper, so packages in custom alphanumeric download categories stay eligible while a row the helper could never name in an exclusion is skipped (sanitized DEBUG) instead of starving later packages. That contract follows the advertised capability, never the presence of a cooldown service. Malformed protected rows are skipped rather than failing selection. Requests without that capability use the exact legacy selector path and ignore the contract, cooldowns, package holds, exclusions, and probes.
- Capable selection is additionally gated by `providers.crypter_cooldowns.crypter_blocks_deferred()`: in `fail` mode `to_decrypt/` builds no `CrypterCooldownService` at all and reads no cooldown state, so persisted cooldown and package defer metadata cannot hold a package. `excluded_package_ids` and the canonical package ID contract still apply in `fail` mode because they are in-flight handout state, not a hold.
- Authenticated `GET`/`POST /api/crypter-block/settings` refreshes/saves the linkcrypter block mode, cooldown hours, and Filecrypt sweep window through `storage.setup.crypter_blocks`. The existing Link Protection section server-renders those cached values, states what each mode does, and saves `mode`, `cooldown_hours`, and `filecrypt_sweep_window_minutes` (null to clear the stored override) through `quasarrApiFetch`; it renders no linkcrypter URL or secret field. The sweep window has a three-level precedence: stored DB override > `FILECRYPT_SWEEP_WINDOW_MINUTES` ENV > default 15. The WebGUI renders a numeric input (1–1440) and a "Use Docker/default value" checkbox; the checkbox being checked sends null (clear override) while unchecked sends the parsed integer.
- The existing Packages page separates only queue rows whose projected `deferred.active` value is true into `Deferred linkcrypter checks`; inactive rows and `fail` mode retain the ordinary protected queue rendering. Cards show sanitized package/linkcrypter/reason labels, observing or cooldown state, evidence, retry countdown, probe state, and - for a live generation only - tested/total, deadline, and retest depth. They never render protected URLs, source hostnames, sweep IDs, operation IDs, or link fingerprints; manual CAPTCHA solving remains linked. Individual and selected-card actions use `quasarrApiFetch` against authenticated `POST /api/packages/deferred/probe` and `DELETE /api/packages/deferred`, both accepting an object with a `package_ids` list. The routes reject a non-list payload before delegation, then preserve the atomic helpers' ordered per-ID results: probe goes through `CrypterCooldownService.request_probe()` and deletion through `downloads.packages.delete_database_packages(..., expected_type="protected")`, never through direct SQLite or JDownloader access.
- Probe additionally honors the block mode: in `fail` mode the route returns `{"success": false, "message": "Linkcrypter blocks are in fail mode"}` before building a `CrypterCooldownService` or touching package defer metadata, because no hold exists to probe and the persisted state must survive a flip back to `defer`. Deletion is not a hold read and stays available in both modes.
- The 5-second `refreshContent()` cycle replaces `#packages-content` wholesale, so it snapshots the checked deferred package IDs immediately before the swap and re-checks only the matching checkboxes the new fragment rendered. The snapshot is local to one cycle (IDs that stopped being rendered are dropped) and matching is `Set` membership against `checkbox.value` - never a selector built from a package value.
- Every ticking countdown is one `.deferred-countdown` element rendered by the shared `_deferred_countdown(attribute, epoch)` helper and carrying the single deadline it counts down to: `data-retry-after-epoch` for the retry countdown and `data-cohort-deadline-epoch` for the cohort deadline. The client resolves it through the one shared `deferredCountdownEpoch(element)` helper as `dataset.cohortDeadlineEpoch ?? dataset.retryAfterEpoch`, so a card carrying only a cohort deadline keeps counting down instead of collapsing to zero on the first tick. Adding a countdown means adding a data attribute to that pair, never a second read or a selector built from rendered data.
- `POST /sponsors_helper/api/defer/` reads the same cached mode through `crypter_blocks_deferred()` (`defer` when the key is absent or holds any other value). `defer` records only validated BLOCKED evidence and returns exactly `hold`, `cooldown`, or `legacy_failure`; `fail` returns the exact available-state `legacy_failure` instruction before constructing or consulting cooldown/package-defer state. Neither mode calls the legacy failure path, deletes protected data, increments failed statistics, or emits FAILED notifications. In `defer`, a package receives at most one provisional hold, while confirmed cooldown always returns the crypter-wide deadline.
- `POST /sponsors_helper/api/crypter-access/` is the sole CLEAR path. It accepts only lowercase `clear`, validates the canonical package ID and protected crypter key, and requires the live package to contain a link resolving to that key. It then proves health first and releases afterwards - it must never clear package defer state before the healthy decision commits.
- Report classification on `/defer/` and `/crypter-access/` is tri-state and decided by what the body carries, never by an advertised capability. A body with neither `sweep_id` nor `offer_id` is ordinary version-one work. A body carrying the complete exact identity - `crypter` literally `filecrypt` with no case or whitespace normalization, 32-lowercase-hex `sweep_id` and `offer_id`, 64-lowercase-hex `link_fingerprint`, plus a string `reason_code` or an `access` of exactly `clear`/`unknown` - is a cohort report. Anything in between is explicit cohort intent the server cannot parse and answers HTTP 400 before reading any state; falling back to the state-changing version-one route would let a typo record an observation and write a hold the helper never asked for. A live sweep or cooldown therefore survives a malformed report byte for byte.
- The Filecrypt cohort protocol lives in `sponsors_helper/cohort_protocol.py` and is pure: no storage, settings, or clock. There are exactly three disjoint compatibility paths. Without `crypter_defer_v1` the helper gets the exact legacy selector and bodies, no contract enforcement, no cooldown service, and no terminal operation ID. With `crypter_defer_v1` alone it gets today's canonical-ID enforcement and package-local version-one behavior. Cohort behavior needs both `crypter_defer_v1` and the exact `filecrypt_cohort_sweep_v1`; the sweep capability alone is not enough.
- CLEAR is independent of later CAPTCHA, extraction, or download outcomes; UNKNOWN has no legacy route call, and `/download/` retains its legacy payload and behavior.
- `/defer/` and `/crypter-access/` classify a report by what it carries, not by an advertised capability: a cohort report is exactly one naming `crypter="filecrypt"` plus a 32-lowercase-hex `sweep_id` and `offer_id` and a 64-lowercase-hex `link_fingerprint`. A body naming no offer at all falls back to the version-one route, which can never delete or overwrite a version-two decision. Cohort access additionally requires `access` to be exactly `clear` or `unknown`.
- Cohort `/defer/` answers `success` plus `instruction`/`state`/`hold_type`/`evidence_count`/`retry_after_epoch` and `sweep_id`/`sweep_tested`/`sweep_total`/`sweep_deadline_epoch`; `stale` is HTTP 200 with `success: true` so it never triggers the helper's version-one local exclusion, and it is what a well-formed identity that is no longer valid receives. Cohort access answers HTTP 200 for a CLEAR (`state`, `cleared`) or an accepted UNKNOWN (`state`, `accepted`), each with `sweep_id`, `offer_id`, and the three counters. Every other access outcome - a superseded lease, a wrong generation, a `fail`-mode bypass, an offer already resolved through the other route, a report whose package is proven not to own the offered link, or a CLEAR whose ownership could not be proven at all - is the same non-destructive `instruction: "stale"` body under HTTP 409. The exact version-one bodies stay six fields.
- The version-one `/defer/` answer is produced by one `CrypterCooldownService.record_version_one_report()` transaction, never by a pre-read plus a separate write: the accumulator, the version-two precedence, and the package hold are all decided against the linkcrypter and package rows current inside that transaction. A cohort decision that opens between an earlier read and the commit therefore answers `legacy_failure` with `hold_type` `none`, retry 0, and no package write at all, while `cooldown` still repeats cooldown and writes its hold.
- Outside `fail` mode a validated version-one CLEAR performs the global healthy transition through `CrypterCooldownService.record_legacy_success(crypter, package_id=...)`, which commits health first and only then runs every physical release as contained best effort, and still returns exactly `{"success": true, "state": "available", "cleared": true}`. A cleanup failure never changes that acknowledgement because the committed window already invalidated those holds logically, and a failed health commit can never have released one. In `fail` mode both access paths mutate nothing and read no state: version one returns that same compatibility body, a cohort report the stale acknowledgement.
- `to_decrypt/` computes the bounded `FilecryptInventory` from the protected rows it already enumerated, before any mutation, and passes an unreadable inventory on as `None` so no transition can cool on it. `prepare_offer()` owns the member choice; the route maps that fingerprint onto its deterministic live occurrence (package ID ascending, then stored link index) and binds the handout to that occurrence's **stored link index**, not to its digest - two raw URLs of one package can normalize to the same fingerprint, and only the selected one may travel. That link is first and is the only Filecrypt URL in the handout. A manual `probe` mode is requested only while a cohort cooldown could issue one, and it names the exact member it can answer: the lowest package ID with a queued Filecrypt probe, and inside it the lowest stored link index its hold still covers. Under a cohort cooldown only that typed handout may spend the queued probe, because an untyped one could only produce a version-one report the cohort decision cannot use. When the offered occurrence is not handable the request falls back to ordinary work and the unanswered lease expires. `select_helper_package()` uses `helper_package_is_candidate()` as its one package predicate, passes the coherent `crypter_projection()` decision into `project_package_defer()`, and calls `package_defer_covers_fingerprint()` per link, so a hold suppresses its own tested link everywhere while a never tested link of the same package stays eligible - a package is never excluded before its links are evaluated.
- Every request advertising both capabilities also receives `terminal_operation_id = sha256("sponsors-helper-terminal-v2\n" + package_id)`, including ordinary work that carries no `crypter_offer`. It is output only here; the terminal-operation endpoints elsewhere in this API verify it.
- An unexpected exception on `to_decrypt/`, `/defer/`, or `/crypter-access/` answers the fixed body `Internal server error` under HTTP 500 through `internal_failure(event, error)`, which logs the fixed event plus `type(error).__name__` on this side only. An exception text can carry a storage path, a release title, or a container URL, and the helper has no use for any of it; `ValueError` validation messages stay HTTP 400 because they describe the request the helper sent.
- `/download/`, `/disable/`, and `/fail/` share one terminal-envelope gate. A body carrying neither `protocol_version` nor `terminal_operation_id` stays on the exact legacy path and retains its plain-text/body semantics. Any body carrying either field must carry `protocol_version` as the non-boolean integer `2`, a non-empty `package_id`, and the exact 64-lowercase-hex `terminal_operation_id(package_id)`; malformed is HTTP 400 before side effects, conflicting package/state reuse is 409, and a full operation table is 503. A conflict is measured against reality before it is refused, because the identity is derived from the package ID and the record found may belong to a life that already closed: a `complete` record of another outcome whose package is protected again under neither its removal nor its own disable is retired through `reopen_completed(..., completed_state=)` and the report is admitted under the terminal state it names, all inside the `exclusive()` block that then runs it. Everything that proves less stays 409 - a record short of `complete` may still own an unfinished side effect, one of a shape that marked no artifact can show neither its outcome nor the life its package is in, a package that never came back is still bound, and a protected package that cannot be read decides nothing. CAPACITY is untouched by this: it is answered only where no row exists at all, so no closed life can be behind it. A stored operation row this build cannot read is also 503 (never 409 or 400): it is preserved byte-identical and authorizes no addLinks, fail, disable, counter, notification, or protected-row removal, because it may already describe an applied effect. Every accepted v2 response has exactly `success`, `terminal_state`, `package_removed`, `package_terminal`, and `package_id`; an ordinary side-effect or cleanup failure remains HTTP 200 with `success: false`, and no route infers removal from a successful storage/JDownloader call without reading the protected row back.
- V2 terminal routes orchestrate only the provider-owned phases, and each one runs its whole decision inside `TerminalOperationService.exclusive()`, so two retries that arrive together are serialized instead of both reading the same phase: the second one re-reads what the first committed and replays. Download persists `prepared`, persists the durable attempt, submits to JDownloader at most once, persists `submitted`, then verifies protected cleanup, notification, and counters before `complete`. The reconciliation trigger is the record's `effect_state`, never the outcome of `begin()`: an operation still marked `not_started` provably changed nothing, so it reads no history and no device state at all and simply applies its transition, and only an operation marked `attempting` reconciles - from failed history carrying its own marker and from the JDownloader comment its own submission travelled with, in that order, with an unavailable answer never authorizing another submission. Fail records its own row unless history already carries its marker; disable applies the flag unless the package already carries its marker, so a stale failed row, a stale JDownloader package or an already-disabled package left by an earlier life of the same release can neither skip the current terminal action nor report a download success without submitting. A complete operation replays its stored terminal flags without side effects only for as long as it still describes the world: while the protected package is gone, and - for the disable that deliberately keeps its package - while that package still carries this operation's own marker. A package ID is derived from the release, so a re-grabbed release is protected again under the identity of every life of it that already closed; a complete record found next to a protected package therefore belongs to a life that ended, and all three confirm functions retire it through `reopen_completed()` and run the fresh operation that opens in its place - submitting, failing or disabling for this life and completing on its own terms. The retirement happens inside the same `exclusive()` block as the operation that follows it, so two retries arriving together still submit once. A protected package that cannot be read proves neither case and answers structured `success=false` without touching the record. Operation records contain no title, URL, password, link, solver, or notification data, and this API never opens SQLite directly.
- Terminal artifacts are marked with `operation_evidence(record)` under the non-secret `terminal_operation` key (failed history JSON, protected package JSON) or inside the submission comment (`submission_comment()`), always written with the artifact itself. The evidence binds package ID **and** the epoch the record opened at, so it is never removed on completion: another operation for the same package can only open a full retention window later, which makes an older life's marker unmatchable by construction.
- A terminal failure is ordered failure row + both counters (one `commit_terminal_failure()` transaction, the commit point) -> notification -> protected removal, and every one of those waits on the previous. A commit that never landed leaves the operation exactly where it was, answers structured HTTP-200 `success=false`, and produces no counter, no notification and no deletion; the protected package therefore survives for the retry. The notification is fenced by the durable `notification_state` pending phase instead of a flag written afterwards, so a lost answer between dispatch and confirmation costs no duplicate message. `record_helper_terminal_failure()` is the one helper all three terminal failure branches use (`/fail/`, an unusable `/download/` payload, and a `phase="submit"` mirror rejection); it adopts a marked row an interrupted attempt left, and then closes that adopted operation's notification unsent, because an artifact of an older shape proves nothing about what followed it. An interrupted `/download/` failure resumes its notification with the reason `failed_package_reason()` reads back, never an invented one. `mark_helper_package_failed()` is the legacy, non-terminal path only.
- A record decoded with `legacy_unproven` is refused before every terminal side effect in all three confirm functions, ahead of the `complete` replay: such a row marked none of its artifacts, so it can show neither that the life it closed is the one its package is in now nor that a fresh operation is owed. Such a record may only read whether the protected package is gone: absent completes it with `package_removed=True` and no counter, notification, `addLinks`, `fail`, disable or deletion, and a `complete` one replays its stored flags there; present answers structured `success=false`, `complete` rows included, and never reopens. An unmarked failed row, an unmarked JDownloader package and an unmarked `disabled: True` flag are never trusted, and their absence is never read as "solved" - the package waits for the operator or for retention to allow a fresh lifecycle.
- Linkcrypter transitions are counted by the `providers/` transaction that performs them, never by this layer: `defer/` and `to_decrypt/` build no `StatsHelper` at all, so no statistics failure can change a defer response, a hold, package selection, or a probe handout, and `select_helper_package()` has no probe callback that could reject a package whose probe was already spent. No defer, CLEAR, or probe path touches failed-download/decryption counters or emits FAILED/DISABLED notifications, and CAPTCHA-solver statistics keep reading `notification.solvers[].name`.
- The statistics page adds `Linkcrypter Blocks`, `Filecrypt cohort`, and `Terminal operations` sections. The provider projection is fixed-cardinality: cumulative observations/cooldowns/probes and the live deferred gauge; current sweep state, tested/total, deadline, cooldown count, healthy retest depth, and fixed individual reason; and prepared/submitted/complete operation counts. No linkcrypter, hostname, URL, package ID, sweep/offer/fingerprint, or operation ID is ever a statistics key or label.
- All userscript bodies come only from `quasarr.providers.obfuscated`; source hostnames come only from `Config("Hostnames")` at runtime.
- `GET /api/hostnames` (API-key-protected, registered beside the existing `POST /api/hostnames` in `api/config/__init__.py`) returns `storage.setup.hostnames.get_hostnames_data()`: a secret-free JSON projection of `build_hostname_rows()` - status/details/timestamp, login/credential *support* plus which config section holds it, FlareSolverr requirement, language, categories, invite/account flags, and skip state per source, including each source's own configured hostname value (this authenticated page owns that configuration), but never a user/password credential value.
- Every protected crypter/source (filecrypt, keeplinks, tolink, junkies, HE) is served the same standardized userscript page via `render_userscript_section`; hide auto-decrypts without a page. HE packages are recognized by their `he` mirror tag or configured runtime hostname. There is no server-side CAPTCHA solving - the userscript solves on the provider's own page and returns links through `GET /captcha/quick-transfer` (manual paste via `POST /captcha/bypass-submit` is the only fallback).

## Work Guidance

- JSON config endpoints return `{success: bool, message: str}` unless they are read endpoints with richer payloads; frontend JS calls protected `/api` endpoints through the global `quasarrApiFetch` helper injected by `html_templates`.
- HTML is built with f-strings (double `{{ }}` for literal CSS/JS braces) via `providers.html_templates` and `providers.html_images`; follow the brace style of the file being edited.
